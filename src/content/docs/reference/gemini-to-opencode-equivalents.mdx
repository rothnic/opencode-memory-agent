## Concept map

| Reference project concept | OpenCode-first replacement |
| --- | --- |
| ADK agent orchestration | Installable OpenCode plugin with internal SDK sessions |
| Gemini model calls | OpenCode-configured provider/model used by the plugin's internal prompts |
| Python app loop | Plugin hooks plus optional Bun-managed subprocesses |
| Direct process logging | `client.app.log()` |
| File watcher inbox | OpenCode file/session events and project watcher config |
| HTTP query endpoint | `memory_query` custom tool backed by stored memory + indexed docs |
| Single `memory.db` file | `.opencode/memory/shared/*.json` + `.opencode/memory/private/*.json` |

## Why this mapping works

OpenCode already provides:

- configurable agents,
- event subscriptions inside plugins,
- an SDK client for sessions, files, and logging,
- tool and permission boundaries.

That removes the need to recreate a parallel agent runtime just to get persistent memory behavior.

## Practical interpretation

The plugin stays responsible for orchestration and storage. Its main jobs are to:

- detect when a memory pass is worth running,
- debounce repeated triggers,
- create short-lived internal SDK sessions for summarization/query work,
- store only curated memory artifacts.

That keeps the installed package self-contained while still using OpenCode-native model execution.
